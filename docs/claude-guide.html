۱کلاد Code چیست؟

Claude Code یک برنامهٔ خط فرمان است که یک مدل زبانی (Claude) را داخل پوشهٔ پروژهٔ شما می‌نشاند. تفاوتش با چت معمولی این است که دسترسی به فایل‌ها و اجرای دستورات دارد: می‌تواند فایل بخواند، ویرایش کند، دستور شل بزند، در مرورگر سایت را باز کند و نتیجه را ببیند.

خودِ Claude هیچ‌چیز دربارهٔ این پروژه نمی‌داند. هر چیزی که می‌داند از دو جا می‌آید:

  • آنچه در همان لحظه می‌خواند (فایل‌ها، خروجی دستورها، صفحهٔ وب).
  • آنچه ما از قبل برایش نوشته‌ایم — همان ساختار .claude/ که موضوع این سند است.
نکتهٔ کلیدی بزرگی و کیفیت کاری که کلاد انجام می‌دهد، بیش از آنکه به «هوش» مدل وابسته باشد، به کانتکستی وابسته است که ما فراهم می‌کنیم. ساختار .claude/ دقیقاً همین است: کانتکست درست، در زمان درست، بدون اینکه همه‌چیز همیشه در حافظه بار شود.

سه واژه‌ای که باید بلد باشید

واژهیعنی
کانتکست (Context)مجموع چیزی که مدل در یک لحظه می‌بیند. پر شدنش باعث فراموشی و افت کیفیت می‌شود.
ابزار (Tool)توانایی عملی مدل: خواندن فایل، اجرای دستور، کلیک در مرورگر. مدل تصمیم می‌گیرد کدام ابزار را کِی صدا بزند.
پرامپت سیستمی (System prompt)متن پنهانی که قبل از گفت‌وگو به مدل داده می‌شود و رفتار و لحنش را تعیین می‌کند. دستورهای پروژه نیز همین‌جا تزریق می‌شوند.

تفاوت «اسکیل» و «ایجنت» — مهم‌ترین تمایز

اسکیل = دانش

یک فایل متنی که می‌گوید «این کار را این‌طور انجام بده». مثل یک چک‌لیست یا دفترچهٔ راهنما. در همان گفت‌وگوی فعلی خوانده می‌شود و کانتکست را پر می‌کند.

ایجنت = کارگر

یک کلاد جداگانه که کار را در پنجرهٔ کانتکست مستقل خودش انجام می‌دهد و فقط نتیجه را برمی‌گرداند. برای جست‌وجوی پهن یا بررسی‌های سنگین، چون کانتکست شما را پاک نگه می‌دارد.

چرا این تفکیک مهم است؟ اگر مدل بخواهد صد فایل را خودش بخواند تا یک چیز را پیدا کند، کانتکست گفت‌وگو پر می‌شود و کیفیت کارش افت می‌کند. راه درست: یک ایجنت بفرست که بگردد و فقط جواب را برگرداند.

۴لایهٔ ۱ — دستورهای همیشه‌بار

این فایل‌ها در ابتدای هر گفت‌وگو خودکار خوانده می‌شوند. پس باید کوتاه باشند؛ هر کلمهٔ اضافه، در هر بار، کانتکست مصرف می‌کند.

CLAUDE.md

فایل اصلی. می‌گوید: این پروژه چیست، استک چیست، «منبع حقیقت» کدام اسناد هستند، چه ثابت‌هایی شکستنی نیستند. دستور @AGENTS.md در خط اول، آن فایل را هم ضمیمه می‌کند.

AGENTS.md

هشداری برای مدل: «این نسخهٔ Next.js با آنچه در آموزش‌هایت دیدی فرق دارد؛ قبل از کد نوشتن، داکیومنت‌های داخل node_modules/next/dist/docs/ را بخوان.» این فایل را خودِ next dev تولید می‌کند.

.claude/rules/project-invariants.md

چیزهایی که هرگز نباید نقض شوند. مثلاً:

  • فارسی/RTL هدف است و الان اعمال شده؛ کلاس‌های فیزیکی مثل ml-4 ممنوع.
  • کلید GEMINI_API_KEY هرگز نباید کلاینت‌نشود.
  • رفتار مخصوص هر دسته باید داده‌محور باشد، نه با if روی نام دسته.
  • فقط یک نام برای آدرس بک‌اند: NEXT_PUBLIC_API_URL.
تفاوت rules/ و docs/ rules/ خودکار بار می‌شود (پس کوتاه و امری است). docs/ بار نمی‌شود و مدل فقط وقتی لازم داشت می‌خواند.

۵لایهٔ ۲ — اسکیل‌ها

اسکیل یک پوشه با یک فایل SKILL.md است. بالای فایل دو خط کلیدی دارد:

---
name: web-testing
description: Use when you need to verify that a page ... actually works ...
---

مدل همیشه فقط name و description همهٔ اسکیل‌ها را می‌بیند (فهرست کوتاه). وقتی موضوع با description بخواند، کل فایل را می‌خواند. به همین دلیل description از «Use when…» شروع می‌شود و فقط شرط استفاده را می‌گوید.

چرا در description خلاصهٔ محتوا نمی‌نویسیم؟ اگر بنویسیم «این اسکیل ۳ مرحله دارد…»، مدل ممکن است همان خلاصه را اجرا کند و اصل فایل را نخواند. شرط استفاده را بنویس، نه راه‌حل را.

۶لایهٔ ۳ — ایجنت‌ها

هر ایجنت یک فایل در .claude/agents/ است با فهرست ابزارهای مجاز. وقتی صدا زده می‌شود، یک کلاد مستقل با کانتکست خالی بالا می‌آید و فقط گزارش نهایی را برمی‌گرداند.

ایجنتکارشابزارها
code-reviewerفقط فایل‌های تغییریافته را برای درستی، قواعد پروژه، امنیت و RTL بررسی می‌کندفقط خواندن + Bash
debuggerخطا را با فرایند ۴ مرحله‌ای root-cause پیدا می‌کندفقط خواندن + Bash
nextjs-feature-builderفیچر جدید می‌سازد (صفحه، کامپوننت، route)خواندن + نوشتن
gemini-search-engineerمخصوص جست‌وجوی Gemini؛ کلید را فقط سمت سرور می‌خواندخواندن + نوشتن

دو ایجنت اول عمداً اجازهٔ نوشتن ندارند. یعنی فقط بررسی می‌کنند و نمی‌توانند خرابی درست کنند. این یک تصمیم طراحی است، نه محدودیت.

۷لایهٔ ۴ — هوک‌ها فعال

هوک یک اسکریپت است که خودِ برنامه و بدون دخالت مدل، روی یک رویداد اجرا می‌کند. این مهم‌ترین تفاوت با اسکیل است: اسکیل «راهنما» است و ممکن است نادیده گرفته شود؛ هوک «قانون» است و دور زدنش ممکن نیست.

در .claude/settings.json دو هوک فعال است:

۱) SessionStart — در شروع هر گفت‌وگو

node "$CLAUDE_PROJECT_DIR/.claude/hooks/session-start.mjs"

یک وضعیت کوچک چاپ می‌کند: قدم بعدی از docs/STATUS.md، هشدار اگر .env.local نبود، و یادآوری بررسی مرورگر. خروجی‌اش:

Lensloop (Persian RTL rental marketplace). Rules in CLAUDE.md + …
Next: Add a test runner (Vitest) — then restore the test gate in …
Verify UI in a browser with the web-testing skill; never claim a page works without loading it.

۲) PostToolUse — بعد از هر Edit/Write

node "$CLAUDE_PROJECT_DIR/.claude/hooks/check-edit.mjs"

هر فایلی که کلاد ویرایش کند، بلافاصله بررسی می‌شود:

  • کلاس فیزیکی RTL مثل ml-4 یا text-left → جلوی ویرایش گرفته می‌شود و مسیر اصلاح را می‌گوید.
  • رنگ خام مثل #ff0000 → ایراد گرفته می‌شود (مگر کامنت allow-hex داشته باشد).
  • خطای ESLint در همان فایل → برگردانده می‌شود تا خودش اصلاح کند.
  • آیکون جهتی → فقط تذکر، بلاک نمی‌کند.

نمونهٔ واقعی خروجی (با یک فایل آزمایشی اجرا شد، کد خروج ۲):

RTL: physical Tailwind classes in probe.tsx (fix: node .claude/scripts/rtl-codemod.mjs --write probe.tsx)
  L1 ml- -> ms-
  L1 text-left -> text-start
TOKENS: raw color literals in probe.tsx; use design tokens …
  L1 #ff0000
exit=2
چرا این بهتر از توضیح دادن به مدل است؟ اگر قاعده را فقط در یک اسکیل بنویسیم، مدل ممکن است زیر فشار (وقت کم، کار زیاد) از آن عبور کند. هوک این امکان را حذف می‌کند: قاعده در سطح ابزار اجرا می‌شود، نه در سطح تصمیم مدل.

مجوزها (permissions)

همان فایل settings.json فهرست سفید و سیاه هم دارد. مثلاً npm run lint بدون سؤال اجرا می‌شود، ولی خواندن .env.local ممنوع است و git push --force بلاک است.

۸لایهٔ ۵ — اسکریپت‌های قطعی

برای کارهایی که قابل تشخیص با قاعده هستند، نباید از مدل استفاده کرد. یک اسکریپت ارزان‌تر، سریع‌تر و تکرارپذیرتر است. اینجا سه اسکریپت داریم:

اسکریپتکار
rtl-rules.mjsمنبع واحد قواعد: فهرست تبدیل‌ها، الگوهای رنگ، CSS فیزیکی. دو اسکریپت دیگر از همین import می‌کنند.
rtl-scan.mjsکل پروژه را می‌گردد؛ اگر تخلف قطعی باشد کد خروج ۱ می‌دهد.
rtl-codemod.mjsتخلف‌ها را خودکار اصلاح می‌کند (--write).

اجرا:

node .claude/scripts/rtl-scan.mjs            # آدیت
node .claude/scripts/rtl-scan.mjs --review   # + موارد نیازمند بازبینی انسانی
node .claude/scripts/rtl-codemod.mjs --write # تعمیر خودکار

۹اسکیل تست وب — مهم‌ترین بخش تست

واقعیت را بدانید این پروژه هیچ تست خودکارِ ثبت‌شده‌ای ندارد: نه Vitest نصب است، نه فایل *.spec.ts، نه playwright.config.ts. پکیج‌اسکریپت‌ها فقط dev، build، start، lint هستند. تنها راه بررسی انتها-به-انتها، همین اسکیل web-testing است.

چرا لازم است؟

عبور npm run build فقط ثابت می‌کند کد کامپایل می‌شود. ثابت نمی‌کند صفحه رندر می‌شود. خرابی‌های رایج این پروژه فقط در زمان اجرا دیده می‌شوند:

  • لیست خالی می‌ماند چون پاسخ API در یک پوشه (envelope) پیچیده شده و کامپوننت انتظار آرایهٔ خام دارد.
  • خطای hydration در کنسول — صفحه سالم به نظر می‌رسد ولی خطا می‌دهد.
  • آدرس /gear/[slug] با یک slug ناموجود به‌جای ۴۰۴، کرش می‌کند.
  • چیدمان RTL در موبایل سرریز می‌کند.
  • مورد واقعی که همین امروز پیدا شد: کاشی‌های دسته در صفحهٔ اصلی به /gear?category=… لینک می‌دهند، ولی صفحهٔ لیست این پارامتر را نمی‌خواند. صفحه بی‌نقص رندر می‌شود، هیچ خطایی در کنسول نیست، ولی فیلتر اعمال نمی‌شود — دقیقاً همان چیزی که تست «فقط رندر می‌شود» از دست می‌دهد.

ابزارش چیست؟

یک اتصال Playwright MCP که به‌صورت پلاگین فعال است. مدل با آن واقعاً مرورگر را کنترل می‌کند: صفحه باز می‌کند، درخت دسترس‌پذیری را می‌گیرد، کلیک و تایپ می‌کند، اسکرین‌شات می‌گیرد و کنسول مرورگر را می‌خواند.

ابزارکاربرد

browser_snapshotدرخت دسترس‌پذیری — منبع اصلی برای دیدن ساختار و متن
browser_console_messagesخواندن خطاهای کنسول — هرگز نباید رد شود
browser_click / browser_type / browser_fill_formتعامل با فرم و دکمه

الگوی گزارش

گزارش باید به همین شکل باشد، بدون پرگویی:

/gear — ✅ loads, 9 cards, console clean
/gear/rentino-camera — ❌ console: "Cannot read properties of undefined (reading 'price')"
/login — ⚠️ renders, but layout overflows at 390px

و در انتها دقیقاً بگویید چه چیزی را بررسی نکردید. «صفحهٔ /gear و /login را چک کردم» با «اپ کار می‌کند» دو ادعای متفاوت است.

قاعدهٔ اصلی و پرچم‌های خطر

صفحه تا وقتی مرورگر واقعی آن را بارگذاری نکرده، تأییدشده نیست. خواندن سورس یا عبور build، فقط ثابت می‌کند کد کامپایل می‌شود.

این‌ها یعنی «توقف کن و واقعاً نگاه کن»:

  • داری می‌نویسی «صفحه کار می‌کند» بدون اینکه در همین نشست آن را باز کرده باشی.
  • از خواندن کامپوننت یا از موفقیت build، رفتار UI را حدس زده‌ای.
  • اسکرین‌شات گرفته‌ای ولی کنسول را نخوانده‌ای.
  • صفحهٔ خالی دیده‌ای و فرض کرده‌ای «داده‌ای نیست»، بدون چک کردن فراخوانی شبکه.

مثال عملی

/web-testing  صفحهٔ /gear و /gear/[slug] را در مرورگر چک کن و
              خطاهای کنسول را گزارش بده

۱۰گردش‌کارهای روزمره

«یک صفحه/فیچر جدید بساز»

  1. مدل nextjs16-app-router و rtl-persian-ui را می‌خواند.
  2. الگوی مشابه موجود در src/ را پیدا می‌کند و همان شکل را تکرار می‌کند.
  3. کد را می‌نویسد — هوک روی هر ویرایش، RTL و ESLint را چک می‌کند.
  4. با web-testing در مرورگر باز می‌کند و تأیید می‌کند.
  5. verification-before-completion: lint و build واقعاً اجرا می‌شوند.
  6. در صورت نیاز، code-reviewer دیف را بررسی می‌کند.

«چیزی خراب است»

  1. ایجنت debugger یا اسکیل systematic-debugging.
  2. اول بازتولید دقیق با همان دستور خطا؛ حدس‌زدن ممنوع.
  3. پیدا کردن ریشه، نه وصله کردن نشانه.
  4. اجرای دوبارهٔ همان دستور به‌عنوان شاهد.

«مطمئن شو آمادهٔ merge است»

  1. node .claude/scripts/rtl-scan.mjs → باید ۰ تخلف قطعی بدهد.
  2. npm run lint و npm run build → باید با کد خروج ۰ تمام شوند.
  3. code-reviewer روی دیف.
  4. صفحات کلیدی با web-testing در مرورگر.
قاعدهٔ طلایی هیچ‌وقت «کار می‌کند» یا «تست‌ها پاس شدند» نگویید، مگر اینکه همان دستور در همان نشست اجرا شده و خروجی‌اش دیده شده باشد. گزارش باید شاهد داشته باشد، نه ادعا.

۱۱مرجع سریع و واژه‌نامه

واژهیعنی
Skill (اسکیل)فایل راهنما که با موضوعش بار می‌شود؛ دانش است نه اجرا
Agent (ایجنت)کلاد جداگانه با کانتکست مستقل؛ کار را انجام می‌دهد و نتیجه را برمی‌گرداند
Hook (هوک)اسکریپتی که خود برنامه روی رویداد اجرا می‌کند؛ اجباری است
MCPپروتکل اتصال ابزارهای بیرونی — اینجا برای کنترل مرورگر (Playwright)
Envelopeپوشش استاندارد پاسخ API این پروژه: { success, message, data }
Logical utilityکلاس‌های Tailwind مثل ms-/me- که در RTL و LTR هر دو درست‌اند

۱۲چه چیزی نداریم (صادقانه)

ساختار بالا خوب است، ولی کامل نیست. این‌ها هنوز وجود ندارند:

نبودیعنی چه

تست e2e ثبت‌شدهتست مرورگر تعاملی است، نه فایل قابل اجرا در CI. برای تکرارپذیری، باید Playwright به‌عنوان devDependency نصب و e2e/*.spec.ts نوشته شود.
اسکریپت‌های npmnpm run rtl:scan وجود ندارد؛ باید مستقیم node .claude/scripts/… زد.
