# فصل ۱۰ - شرح تکنولوژی‌های مورد استفاده

## ۱۰-۱. نمای کلی معماری

رنتینو یک برنامۀ دولایه (Two-Tier) با معماری کلاینت-سرور است. جدول ۱۰-۱ سه لایۀ آن را از بالا به پایین نشان می‌دهد.

**جدول ۱۰-۱. لایه‌های معماری و مسئولیت هر لایه**

| لایه | مؤلفه‌های اصلی | نقش |
|---|---|---|
| مرورگر کاربر | Next.js ۱۶ با App Router، React ۱۹، Tailwind CSS ۴، shadcn/ui روی Radix | رندر رابط فارسی و راست‌به‌چپ، تعامل کاربر |
| API | NestJS ۱۱ با پیشوند `/api/v1`، احراز هویت JWT، کنترل نقش، اعتبارسنجی DTO، Swagger | منطق کسب‌وکار و مرز اعتماد |
| داده | Prisma ۶ و PostgreSQL ۱۷؛ ۹ مدل داده؛ تراکنش سریال‌پذیر برای رزرو | ذخیره‌سازی و جلوگیری از تداخل تاریخ |

ارتباط مرورگر با API از طریق HTTPS و کوکی `httpOnly` انجام می‌شود و ارتباط API با پایگاه داده با SQL و از طریق Prisma است.

**نکتۀ مهم:** پیش از این، برخی اسناد پروژه بک‌اند را «خارجی و خارج از مخزن» توصیف می‌کردند. بازبینی کد در تاریخ ۲۵ مهر ۱۴۰۵ نشان می‌دهد که یک بک‌اند NestJS کامل در پوشۀ `backend/` وجود دارد. این سند بر پایۀ کد موجود نوشته شده است، نه اسناد قدیمی.

**جدول ۱۰-۲. فناوری‌های فرانت‌اند**

|---|---|---|---|
| Next.js | ۱۶.۳.۰ | چارچوب React با App Router | مسیریابی مبتنی بر فایل، رندر سمت سرور برای صفحات عمومی، تقسیم کد خودکار |
| React | ۱۹.۲.۸ | کتابخانۀ رابط کاربری | مدل کامپوننتی، اکوسیستم بالغ، پشتیبانی از Server Components |

| lucide-react | - | آیکون‌ها | سبک، سازگار با اندازه‌های مختلف |

**الگوی مسیریابی:** مسیرهای عمومی (`/`، `/gear`، `/gear/[slug]`، `/blog`، صفحات ثابت) و مسیرهای محافظت‌شدۀ داشبورد (`/dashboard/customer`، `/dashboard/provider`، `/dashboard/admin`) در App Router تعریف شده‌اند. هر داشبورد، لایۀ محافظ نقش خود را دارد.

**لایۀ ارتباط با API:** یک پوشش (Wrapper) تایپ‌شدۀ `fetch` در `src/lib/api.ts` وجود دارد که کوکی‌ها را ارسال می‌کند و در پاسخ ۴۰۱، یک بار تلاش برای تازه‌سازی نشست انجام می‌دهد. این الگو، منطق احراز هویت را از کامپوننت‌ها جدا می‌کند.

**فارسی و RTL:** ریشۀ سند با `lang="fa" dir="rtl"` تنظیم شده و فونت وزیرمتن به‌صورت خودمیزبان بارگذاری می‌شود. اعداد فارسی، نرمال‌سازی حروف عربی/فارسی و تاریخ شمسی در `src/lib/format.ts` پیاده‌سازی شده‌اند. قواعد پروژه، استفاده از ویژگی‌های منطقی Tailwind (`ms/me/ps/pe/start/end/text-start`) را الزامی می‌کند و ویژگی‌های فیزیکی (`ml/mr/pl/pr/left/right`) را مسدود می‌کند.

**پیشوند و نسخه‌بندی API:** همۀ مسیرها زیر `/api/v1` قرار دارند (به‌جز `health`). نسخه‌بندی مسیر، امکان تغییر سازگار در آینده را فراهم می‌کند.

**مستندسازی:** Swagger در مسیر `/docs` فعال است و احراز هویت کوکی را توصیف می‌کند. این مستندسازی، مبنای قرارداد بین فرانت‌اند و بک‌اند است.

## ۱۰-۴. مدل داده

طرح‌وارۀ Prisma نُه مدل اصلی دارد:

| مدل | نقش | نکات کلیدی |
|---|---|---|
| `User` | کاربران | نقش CUSTOMER/PROVIDER/ADMIN؛ وضعیت ACTIVE/SUSPENDED |
| `RefreshToken` | نشست‌های تازه‌سازی | ذخیرۀ هش SHA-256؛ یکتا بودن هش |
| `Category` | دسته‌بندی کالا | اسلاگ یکتا؛ رابطه با کالاها |
| `GearItem` | کالای قابل اجاره | قیمت به ریال صحیح؛ `stock` و `availableStock`؛ `specifications` از نوع JSON |
| `RentalOrder` | سفارش اجاره | وضعیت چرخۀ عمر؛ بازۀ تاریخ؛ مالکیت مشتری/ارائه‌دهنده |
| `RentalOrderItem` | اقلام سفارش | پشتیبانی از سفارش چندکالایی |
| `Payment` | پرداخت | وضعیت PENDING/COMPLETED/FAILED؛ یکتا بودن پرداخت هر سفارش |
| `Review` | نظر و امتیاز | یکتا بودن نظر هر مشتری برای هر کالا |
| `BlogPost` | محتوای بلاگ | وضعیت انتشار و اسلاگ |

**تصمیم‌های طراحی داده:**

1. **پول به‌صورت عدد صحیح ریال:** جلوگیری از خطای اعشار شناور در محاسبات مالی.
2. **تاریخ پایان انحصاری:** بازۀ `[startDate, endDate)` به این معناست که روز پایان، برای رزرو بعدی آزاد است. این تصمیم، ابهام «شب آخر» را حذف می‌کند.
3. **`specifications` به‌صورت JSON:** ویژگی‌های هر دسته (مثلاً ISO دوربین، تعداد دستۀ کنسول) بدون تغییر طرح‌واره قابل افزودن است. این تصمیم با قاعدۀ «رفتار دسته‌محور، داده‌محور باشد» سازگار است.
4. **موجودی قابل رزرو:** `availableStock` از `stock` جدا نگه داشته می‌شود تا رزروهای فعال، موجودی قابل فروش/اجاره را کاهش دهند.
5. **یکتایی پرداخت هر سفارش و نظر هر مشتری/کالا:** این قیدها از تکرار تراکنش و نظر تکراری در سطح پایگاه داده جلوگیری می‌کنند.

## ۱۰-۵. احراز هویت و امنیت

**مدل احراز هویت:**

- ورود با ایمیل و رمز؛ رمز با bcryptjs درهم‌سازی می‌شود.
- توکن دسترسی با عمر ۱۵ دقیقه و توکن تازه‌سازی با عمر ۷ روز صادر می‌شود.
- هر دو توکن در کوکی `httpOnly` قرار می‌گیرند؛ در تولید `secure` و با `sameSite=lax` تنظیم می‌شوند.
- توکن تازه‌سازی به‌صورت هش SHA-256 در پایگاه داده ذخیره می‌شود؛ توکن خام در سرور نگه داشته نمی‌شود.
- در هر تازه‌سازی، توکن قبلی ابطال و توکن جدید صادر می‌شود (Refresh Rotation).
- کنترل نقش با `RolesGuard` و دکوراتور `@Roles()` انجام می‌شود.
- بررسی مالکیت منبع (مثلاً کالای ارائه‌دهنده یا سفارش مشتری) در سرویس انجام می‌شود.

**چرا کوکی httpOnly و نه localStorage؟** توکن در localStorage برای جاوااسکریپت قابل خواندن است و در صورت XSS، سرقت توکن آسان می‌شود. کوکی httpOnly این سطح از دسترسی را حذف می‌کند؛ در عوض، نیازمند محافظت CSRF و تنظیم دقیق `sameSite` است. در این پروژه، `sameSite=lax` و CORS با credentials تنظیم شده است.

**اعتبارسنجی ورودی:** `ValidationPipe` سراسری، DTOها را با class-validator بررسی می‌کند و از ورود دادۀ نامعتبر به سرویس جلوگیری می‌کند.

**مدیریت رمز و راز:** کلیدهای سمت سرور (مانند `GEMINI_API_KEY` در قابلیت آیندۀ جست‌وجوی هوش مصنوعی) نباید به کلاینت منتقل شوند. متغیرهای عمومی فرانت‌اند فقط شامل آدرس API و تنظیمات غیرحساس‌اند.

**پرداخت:** پرداخت در MVP شبیه‌سازی‌شده است (`method = "SIMULATED"`). هیچ شمارۀ کارت، CVV یا دادۀ بانکی واقعی ذخیره نمی‌شود. صفحۀ درگاه شبیه‌سازی‌شده فقط برای نمایش جریان پرداخت است.

## ۱۰-۶. آزمون و ابزارهای کیفیت

**وضعیت تأییدشده در این بازبینی:**

| بررسی | فرمان | نتیجه |
|---|---|---|
| آزمون واحد بک‌اند | `npm test` در `backend/` | ۴ مجموعه، ۲۰ آزمون، همگی موفق |
| بررسی نوع بک‌اند | `npm run typecheck` | خروج ۰ |
| لینت بک‌اند | `npm run lint` | خروج ۰ |
| ساخت بک‌اند | `npm run build` | خروج ۰ |
| بررسی نوع فرانت‌اند | `npx tsc --noEmit` | خروج ۰ |
| لینت فرانت‌اند | `npm run lint` | خروج ۰ با ۹ هشدار |
| ساخت فرانت‌اند | `npm run build` | خروج ۰؛ ۳۴ مسیر |
| آزمون سرتاسری بک‌اند | `npm run test:e2e` | **ناموفق**؛ پایگاه دادۀ آزمون جدول ندارد |

**توضیح آزمون سرتاسری:** مجموعۀ e2e وجود دارد، اما اجرای آن در این محیط با خطای «جدول `Payment` در پایگاه دادۀ جاری وجود ندارد» متوقف شد. علت، خالی بودن پایگاه دادۀ `rentino_test` و اعمال‌نشدن مهاجرت‌هاست. این وضعیت به معنای «نبود آزمون» نیست؛ به معنای «آماده‌نبودن محیط آزمون» است. برای اجرای موفق، باید مهاجرت‌ها روی پایگاه دادۀ آزمون اعمال شوند؛ این اقدام نیازمند تأیید مالک پروژه است.

**ابزارهای کیفیت:** ESLint، TypeScript strict، و اسکریپت‌های RTL برای بررسی ویژگی‌های فیزیکی. آزمون رابط کاربری در مرورگر واقعی، بخشی از رویۀ پذیرش پروژه است.

## ۱۰-۷. انتخاب‌های فناوری و جایگزین‌ها

**جدول ۱۰-۴. تصمیم‌های فناوری**

| نیاز | انتخاب | جایگزین بررسی‌شده | دلیل ترجیح |
|---|---|---|---|
| رابط کاربری فارسی/RTL | Next.js + Tailwind + shadcn | Vue/Nuxt؛ Angular | App Router و Server Components؛ اکوسیستم shadcn؛ کنترل کامل RTL |
| قرارداد نوعی end-to-end | TypeScript + Prisma | JavaScript + Knex | نوع‌های تولیدشده از طرح‌واره؛ کاهش خطای مرز API |
| پایگاه دادۀ تراکنشی | PostgreSQL | MySQL؛ MongoDB | تراکنش قوی برای رزرو؛ JSON برای مشخصات؛ بلوغ |
| احراز هویت امن | JWT در کوکی httpOnly | JWT در localStorage؛ Session | کاهش سطح حملۀ XSS؛ چرخش توکن |
| مستندسازی API | Swagger/OpenAPI | Markdown دستی | تولید از کد؛ هم‌خوانی با پیاده‌سازی |
| آزمون | Jest | Vitest | یکپارچگی با NestJS و ابزارهای موجود |
| جست‌وجوی هوش مصنوعی (آینده) | Gemini API | مدل محلی؛ جست‌وجوی کلیدواژه‌ای | کیفیت تفسیر زبان طبیعی فارسی؛ هزینۀ عملیاتی پایین در MVP |

**چرا یکپارچه‌سازی کامل با هوش مصنوعی در MVP نیست؟** جست‌وجوی زبان طبیعی نیازمند دادۀ ساختاریافته، ارزیابی دقت و مدیریت هزینه است. بدون جست‌وجوی پایه و دادۀ کافی، افزودن AI ارزش واقعی ایجاد نمی‌کند و ریسک وابستگی به تأمین‌کننده را افزایش می‌دهد. بنابراین در فاز یک، جست‌وجوی کلیدواژه‌ای و فیلتر ساختاریافته مبناست و AI به‌عنوان لایۀ تمایز در فاز بعد طراحی می‌شود.

## ۱۰-۸. محدودیت‌های فنی شناخته‌شده

1. **ورود با گوگل:** مسیر بک‌اند فعلی پاسخ ۵۰۱ برمی‌گرداند؛ این قابلیت در استقرار فعلی فعال نیست.
2. **پرداخت واقعی:** فقط شبیه‌سازی است؛ اتصال به درگاه مجاز، کار فاز بعد است.
3. **ودیعه و بیمه:** در مدل داده و فرایند، پیاده‌سازی نشده‌اند.
4. **آزمون سرتاسری:** محیط پایگاه دادۀ آزمون آماده نیست.
5. **لینک عمیق دسته:** فرانت‌اند پارامتر `category` را از URL نمی‌خواند.
6. **اسناد قدیمی:** `docs/STATUS.md` و `docs/ARCHITECTURE.md` وضعیت بک‌اند را قدیمی توصیف می‌کنند؛ کد موجود، منبع حقیقت است.

## ۱۰-۹. جمع‌بندی

1. **پشتۀ فناوری، بالغ و متناسب با دامنه است:** Next.js/React برای رابط فارسی، NestJS/Prisma/PostgreSQL برای معاملۀ تراکنشی.
2. **امنیت نشست، آگاهانه طراحی شده است:** کوکی httpOnly، چرخش توکن، هش توکن تازه‌سازی و کنترل نقش.
3. **مدل داده، نیازهای اصلی را پوشش می‌دهد:** کالا، سفارش، پرداخت، نظر و دسته با قیدهای یکتایی مناسب.
4. **شکاف‌ها شفاف‌اند:** پرداخت واقعی، ودیعه، تأیید هویت و آزمون سرتاسری، کارهای فاز بعدند.
